# Sistema de Gerenciamento para Consultório Odontológico

## Objetivo

Desenvolver um aplicativo de gerenciamento para consultórios odontológicos utilizando **.NET MAUI + Blazor Hybrid**, com foco em:

- Cadastro de pacientes
- Anamnese
- Agenda de consultas
- Financeiro/Cobranças
- Sincronização com Google Agenda
- Possibilidade de expansão para versão Web e Mobile

---

# Stack Tecnológica

## Front-end

- .NET MAUI
- Blazor Hybrid
- MudBlazor (UI principal)

## Banco de dados

Dois modos de operação:

### Offline
- SQLite
- Entity Framework Core

### Online
- Firebase Firestore

## Autenticação

Em modo online:

- Firebase Authentication

---

# Arquitetura

Separar o projeto em camadas.

```
Clinica.Shared.Domain
Clinica.Shared.Application
Clinica.Infrastructure.SQLite
Clinica.Infrastructure.Firebase
Clinica.Infrastructure.GoogleCalendar
Clinica.App.Maui
```

A ideia é que toda a regra de negócio permaneça independente da tecnologia de armazenamento.

# Modos de funcionamento

## Offline

Objetivo:

Funcionar completamente sem internet.

Fluxo:

SQLite

↓

Sistema

↓

Quando houver internet

↓

Sincroniza com Google Agenda

Não depende do Firebase.

---

## Online

Objetivo:

Permitir uso em vários computadores e celulares.

Fluxo:

Firebase Firestore

↓

Sistema

↓

Google Calendar

Todos os dispositivos compartilham a mesma base.

---

# Firebase

Objetivos:

- Sincronização em nuvem
- Multi-dispositivo
- Backup
- Compartilhamento entre computador e celular

Possíveis serviços:

- Firestore
- Firebase Authentication
- Firebase Storage (para documentos e imagens)

Plano Spark (gratuito) atende bem um consultório pequeno.

---

# Sincronização

Criar um serviço dedicado.

Exemplo:

```
ICalendarSyncService
```

Responsável por:

- Criar eventos
- Atualizar eventos
- Excluir eventos
- Comparar alterações

Nunca misturar essa lógica com AgendaService.

Minha única sugestão de mudança

Depois de entender o projeto, eu faria uma pequena alteração na arquitetura:

Em vez de dois modos (Offline e Online), faria um modo híbrido desde o início.

SQLite seria sempre o banco local (cache e funcionamento offline).
Firestore seria a sincronização na nuvem.
O usuário nem precisaria saber se está "offline" ou "online": quando houver internet, o app sincroniza automaticamente.

Isso traz algumas vantagens:

Funciona sem internet.
O computador continua rápido.
O celular usa os mesmos dados.
O Firebase vira backup automático.
A futura versão Web reutiliza a mesma base.
É exatamente o modelo adotado por aplicativos como WhatsApp, Notion, Todoist e Google Keep.

Se eu fosse começar esse projeto hoje, essa seria a arquitetura que eu escolheria. Ela exige um pouco mais de planejamento no início, mas evita uma futura migração de "modo offline" para "modo online".
